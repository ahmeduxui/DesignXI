# Case Study Insights — Patterns from Real Arabic/Saudi UX Projects

Synthesized from 7 professional Behance case studies:
- **Myclass** — EdTech mobile app (Saudi Arabia)
- **Mrsool Redesign** — Food/courier delivery app (Saudi Arabia)
- **Speed Service** — Home services app
- **Store Flo** — Retail/inventory SaaS
- **TRSEAH** — Government/SaaS tender platform (Saudi Arabia, Arabic-first)
- **Ninja Grocery** — Grocery delivery app (2 separate case studies)

These are the norms. Use them as calibration benchmarks.

---

## 1. Timeline & Project Structure

### Standard Timeline
- **Total project length:** 12–16 weeks (3–4 months)
- **Phase breakdown (approximate):**
  - Discover/Empathize: 2–3 weeks
  - Define/Analyze: 2–3 weeks
  - Ideate/Design: 3–4 weeks
  - Prototype/Test/Deliver: 3–4 weeks

### Gantt Chart Pattern
Always present a Gantt-style timeline visual. Phases overlap slightly (define begins before discover fully ends). Label weeks, not month names. Show current phase highlighted.

### Phase Naming Convention
Use one of these two conventions consistently throughout the deliverable:
```
Option A (Human-Centered): Empathize → Define → Ideate → Prototype → Test
Option B (Double Diamond): Discover → Define → Develop → Deliver
```
Pick one and stick to it. Never mix them.

## 2. Research — Quantitative Standards

### Interview Count
- **Minimum:** 8–10 user interviews
- **Typical range:** 10–30
- **Saudi professional projects:** 10–40 (larger range for government/enterprise)

### Survey Count
- **Minimum:** 50 responses (below this loses credibility)
- **Typical range:** 128–177 responses
- **Delivery method:** Google Forms (always mentioned explicitly)
- **Recruitment method:** Purposive sampling, not random

### Statistics Summary Bar (always include)
Every case study opens with a summary bar of numbers:
```
[N] User Interviews  |  [N] Survey Responses  |  [N] Competitors  |  [N] Screens Designed
```
These numbers appear again in the case study header. Make them specific. Never round to clean numbers (127 looks more credible than 130).

## 3. Research — Qualitative Standards

### Stakeholder Interviews
Structure: 4–5 research objectives, each with 2–3 sub-questions.

Standard objective categories:
1. Business goals and vision
2. Definition of success / KPIs
3. Key obstacles and risks
4. Competitive landscape (their perception)
5. Target user profile (their perception — to compare with actual user research)

### User Interviews
Structure: 3–5 research objectives, each with 2–4 questions.

Standard objective categories:
1. Background and context of use
2. Current behavior / existing workarounds
3. Pain points and frustrations
4. Motivators and goals
5. Feature reactions / concept validation (if applicable)

**Always organize interview questions under their research objective — never as a flat list.**

### Recruitment for Interviews
- Mix of acquaintances and strangers
- Screened by: age range, usage habits, relevant demographic
- Conducted via: Zoom, in-person, WhatsApp call (Saudi context)
- Document who was interviewed: [Name, Age, Occupation] or anonymized profile

## 4. Competitor Analysis

### Competitor Matrix Format
- **Number of competitors:** 5–7 apps
- **Feature count evaluated:** 8–15 features per competitor
- **Rating system:** Either `✓ / ✗ / ◑` or `High / Medium / Low` (pick one, never mix)
- **Layout:** Competitors as columns, features as rows

### Saudi Market Competitor Landscape by Category
```
Grocery delivery:     Nana, Noon, HungerStation, Careem, Talabat
Food delivery:        Mrsool, HungerStation, Jahez, Careem, Talabat
Education/EdTech:     Madresty, Faheem, Google Classroom, Classera
Home services:        UrWay, Bakhsh, TaskUs, local competitors
Government/SaaS:      Etimad, Tender.gov.sa, SAP Ariba
```

### Positioning Gap
After the matrix, always show a 2×2 positioning map:
- X-axis: Price (Low → High) or Ease of Use (Complex → Simple)
- Y-axis: Service Breadth (Narrow → Wide) or Speed (Slow → Fast)
- Mark existing competitors + show whitespace where the new product should sit

## 5. Define Phase Deliverables

### Persona Card Structure (exact columns)
Every persona must have these 4 sections as columns or quadrants:
```
Goals          | Motivators
Frustrations   | Behaviors
```

Additional required persona elements:
- Full name (Arabic name for Saudi market, e.g., Nora Abdullah, Rayan Al-Harbi)
- Age + occupation + location (city, Saudi Arabia)
- Representative photo (illustrated or stock — never a real person's photo)
- Quote (1–2 sentences, first person, in the user's voice — not a paraphrase)
- Personality sliders (6–8 axes, see below)
- Favorite brands (4–6 brands the persona would recognizably use)

### Personality Sliders (6–8 axes typical)
```
Introvert ◀────────────────▶ Extrovert
Analytical ◀───────────────▶ Creative
Budget-conscious ◀─────────▶ Quality-focused
Tech-averse ◀──────────────▶ Tech-savvy
Spontaneous ◀──────────────▶ Planned
Independent ◀──────────────▶ Social/collaborative
```
Slider positions must reflect actual research findings — not arbitrary placement.

### Favorite Brands (Saudi market calibration)
Brands that recur across Saudi personas:
```
Lifestyle: Nike, Adidas, Zara, H&M, Lululemon
Tech: Apple, Samsung, Huawei, HP
Automotive: Hyundai, Toyota, Land Cruiser (aspirational)
Food: McDonald's, Starbucks, local chains (Al Baik, Herfy)
E-commerce: Noon, Amazon.sa, Namshi
```
Match brands to the persona's age, income, and interests. A 22-year-old student and a 38-year-old manager have different brand profiles.

### Empathy Map
Four quadrants, labeled exactly:
```
SAYS (direct quotes from research)
THINKS (internal thoughts, worries they don't voice)
DOES (observable behaviors, actions taken)
FEELS (emotions — use feeling words, not thoughts)
```
Each quadrant: 3–5 items minimum. Items must come from actual research, not invented.

### Affinity Map
- Group research findings into 6–8 thematic clusters
- Cluster names are verbs + nouns describing the theme (not vague labels)
  - Good: "Struggling to track order status", "Wanting faster checkout"
  - Bad: "User experience", "App features"
- Use sticky-note visual with color coding per cluster
- Total sticky notes shown: 20–40

### User Journey Map
Five rows, applied to 5–6 journey phases:

**Phases (adjust to product context):**
```
Grocery/delivery:   Awareness → Search → Compare → Order → Track → Receive
Service apps:       Awareness → Explore → Book → During Service → Review
EdTech:             Awareness → Enroll → Learn → Practice → Achieve
```

**Five mandatory rows:**
1. **Phases** — the stage names
2. **Actions** — what the user does at each phase
3. **Goals / Thoughts** — what they're thinking or trying to achieve
4. **Feelings / Emotions** — emotional state (use arc line + words)
5. **Pain Points** — specific frustrations at this phase

**Emotional arc rule:** The arc must not be uniformly positive. It should dip at pain points. A flat happy arc is a red flag that the research wasn't real.

## 6. HMW → Features Mapping

### How Might We Statement Format
```
Issue (from research): [Direct finding]
HMW: How might we [verb] [user] so that [positive outcome]?
Features it drives: [Feature 1], [Feature 2]
```

**Example:**
```
Issue: Users abandon cart because they can't estimate delivery time.
HMW: How might we give users real-time visibility into delivery timing
     so that they feel confident completing their order?
Features: Live delivery tracker, ETA on product detail page, SMS alerts
```

Minimum 5 HMW statements. Each one traces directly to research evidence.

### Feature Prioritization
Use a Priority Matrix:
- **Must Have (P0):** Addresses core user need; product unusable without it
- **Should Have (P1):** Significant UX improvement; high effort justified
- **Could Have (P2):** Nice to have; deprioritized for V1

Every feature in the list must be traceable to a specific HMW statement.

## 7. Ideation Methods

### Crazy 8's
- Show 8 distinct ideas (hand-drawn or rough digital wireframes)
- Ideas must be genuinely different — not color variations of the same layout
- Include Arabic sketches where relevant (labels in Arabic, RTL direction visible)
- Timestamp or vote indicators showing which ideas moved forward

### Card Sorting
- Participants: 13–20
- Method: Open card sort (participants name groups) then closed (validate IA)
- Tool: OptimalSort, Miro, or physical cards
- Output: Dendrogram or similarity matrix showing cluster agreement
- Use results to inform: navigation labels, IA hierarchy, category names

### Impact/Effort Matrix
4-quadrant matrix for feature prioritization:
```
High Impact / Low Effort  → Quick Wins (build first)
High Impact / High Effort → Strategic bets (plan for V2)
Low Impact / Low Effort   → Fill-ins (build if time allows)
Low Impact / High Effort  → Time sinks (eliminate)
```

## 8. Visual Design Patterns

### Typography — Arabic/Saudi Market
```
Display/Headers (Arabic): Stacion, Cairo Display, Almarai
Body (Arabic):            Tajawal, Alexandria, Almarai
Bilingual pairing:        [Western font] + Tajawal (safe universal combo)
Avoid:                    System Arabic (looks unpolished in case studies)
```

### Color Psychology — Saudi Market Norms
```
Delivery/courier apps:    Blue or teal primary (trust, speed)
Grocery/food:             Green or orange (freshness, appetite)
Government/SaaS:          Blue or purple (authority, professionalism)
Luxury/fashion:           Black, gold, or deep navy
EdTech:                   Purple or blue (intelligence, calm)
Healthcare:               Teal or green (wellness, clinical)
```

### Color Scale Standard
Every project defines a full 11-stop scale per color:
```
50 (near-white) → 100 → 200 → 300 → 400 → 500 (base) → 600 → 700 → 800 → 900 → 950 (near-black)
```
- 500 is the interactive/primary color
- 600 is hover state
- 700 is active/pressed state
- 50–100 are background tints

### Bilingual Design
All projects are bilingual (Arabic + English). Design decisions:
- Arabic RTL layout is the primary deliverable, not an afterthought
- Bilingual nav: English label + Arabic label, or language switcher
- Arabic and English content must have equal visual weight
- Font sizes may differ between languages (Arabic often needs +1–2px for readability)

## 9. Case Study Presentation Patterns

### Cover Slide
- App name + Arabic wordmark
- Hero device mockup (phone or laptop, realistic shadow)
- One-line problem statement
- Color palette preview (3–5 swatches)
- Project metadata: Category | Platform | Year | Tools Used

### Project Metadata Block
Always displayed early in the case study:
```
Location:      [City, Country]
Project Type:  [Client / Academic / Personal]
Category:      [EdTech / Food Delivery / SaaS / etc.]
Date:          [Month Year – Month Year]
Tools:         [Figma, Adobe XD, Miro, FigJam, etc.]
```

### Problem/Solution Boxes
- Always paired: one Problem statement + one Solution statement side by side
- Problem: specific, describes a real user pain with measurable impact if possible
- Solution: maps directly to the problem (not a general improvement statement)

**Example pair:**
```
Problem: Users spend 4–7 minutes searching for products due to unclear
         category structure, leading to 38% cart abandonment.

Solution: Restructured IA with smart search + product discovery flow,
          reducing average search-to-cart time by 60%.
```

### Section Headers as Questions
Strong case studies use rhetorical section headers:
- "How did we understand our users?"
- "What did the data reveal?"
- "How might we solve this?"
- "What does the final experience look like?"

This creates narrative pull. Avoid flat headers like "Research" or "Design Phase."

### Quote Callouts
Include 2–4 quote cards throughout the case study:
- Real verbatim quotes from user interviews (not paraphrased)
- Display as large pull-quotes with user identifier (e.g., "— Nora, 27, Riyadh")
- In Arabic when the interview was conducted in Arabic

### Screen Annotation Pattern
When showcasing UI screens, add callout annotations explaining:
- What the UI region does
- Why it was designed this way (design decision)
- How it solves a specific pain point from research

Don't just show pretty screens — explain the decisions.

### Before/After Comparisons
Used when redesigning existing products (Mrsool, Ninja):
- Show the same specific screen or user task — not different features
- Side-by-side: Before (old) | After (new)
- Add annotation arrows pointing to specific improvements
- Frame as: "Users struggled with X → We redesigned to achieve Y"

### Social Media Mockups
Several case studies include social media post mockups (Instagram, Twitter/X, Snapchat). Include if the product has a marketing component.

### Lessons Learned Section
End with 3–5 honest lessons:
- Must be specific to this project — not generic design wisdom
- Include at least one thing that didn't go as planned
- Frame as: "We learned that..." or "Next time, we would..."

**Bad (generic):** "User research is important."
**Good (specific):** "We learned that our initial IA was based on internal assumptions — card sorting revealed users grouped categories by frequency of use, not by product type, which changed our entire navigation structure."

## 10. Deliverables Checklist (Saudi market standard)

A complete Saudi-market UX project typically includes:
```
□ Problem statement (specific, measurable)
□ Research plan / timeline
□ Stakeholder interview findings
□ User interview findings
□ Survey data with donut charts
□ Competitor matrix (5–7 apps, ✓/✗/◑)
□ Positioning map (2×2)
□ Persona card (4 columns, personality sliders, favorite brands)
□ Empathy map (4 quadrants, real quotes)
□ Affinity map (6–8 clusters)
□ User journey map (5 rows, emotional arc)
□ HMW statements (5+, mapped to features)
□ Crazy 8's (8 distinct ideas)
□ Card sorting results
□ Site map
□ User flows (primary task + edge cases)
□ Low-fidelity wireframes
□ High-fidelity screens (Arabic RTL primary)
□ Component library
□ Design system (colors, typography, spacing)
□ Interactive prototype
□ Usability testing results
□ Before/After comparison (if redesign)
□ Developer handoff specs
□ Social media mockups (if applicable)
□ Lessons learned
```
